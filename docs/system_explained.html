1. ภาพรวมระบบและเป้าหมาย

1.1 ปัญหาที่ระบบแก้

นักศึกษา ม.อ. ต้องการ 2 อย่างที่มักแยกกันอยู่: (1) คนที่เข้ากันได้จริง ไม่ใช่แค่หน้าตาหรือคณะ และ (2) คำแนะนำเรื่องความสัมพันธ์ที่เชื่อถือได้ ไม่ใช่ความเห็นลอยๆ จากอินเทอร์เน็ต ระบบนี้รวมทั้งสองอย่างไว้ใน LINE OA ตัวเดียว เพื่อให้ใช้ได้ในแอปที่นักศึกษาเปิดอยู่แล้วทุกวัน ไม่ต้องติดตั้งแอปใหม่

1.2 ความสามารถหลัก

ถามบอตตอบจากคลังความรู้ 37 แหล่งพร้อมอ้างอิงชื่อเอกสาร ถามต่อเนื่องได้คำแนะนำตรวจสอบได้ ไม่แต่งเอง
โปรไฟล์แสดงทุกอย่างที่บอทจำเกี่ยวกับผู้ใช้ความโปร่งใส ผู้ใช้รู้ว่าระบบเก็บอะไร

3. การรับ-ส่งข้อความผ่าน LINE

3.1 Webhook และลายเซ็น

LINE ส่งทุกเหตุการณ์ (ข้อความ, กดปุ่ม, เพิ่มเพื่อน, บล็อก) มาที่ POST /callback ระบบตรวจ ลายเซ็น HMAC-SHA256 ด้วย channel secret ก่อนทุกครั้ง

ทำเพื่ออะไร: ป้องกันคนอื่นปลอมคำขอมาที่ server (เช่น ส่ง event "ลบข้อมูล" ของผู้ใช้คนอื่น) ถ้าลายเซ็นไม่ถูกต้องตอบ 401 ทันที

3.2 ตอบ 200 ทันที แล้วประมวลผลเบื้องหลัง

server ตอบ LINE ว่าได้รับแล้วทันที แล้วค่อยประมวลผลใน background task

ทำเพื่ออะไร: LINE จะส่งซ้ำถ้า webhook ตอบช้า การตอบก่อนป้องกันข้อความซ้ำ ส่วนคำตอบจริงส่งทีหลังด้วย reply token

3.3 Reply กับ Push

  • Reply ใช้ reply token ที่มากับข้อความ ใช้ได้ครั้งเดียวและหมดอายุราว 1 นาที ไม่นับโควตาข้อความ
  • Push ส่งหาใครก็ได้เมื่อไรก็ได้ แต่ นับโควตา ของ OA
  • ระบบใช้ reply ถ้าประมวลผลเสร็จภายใน 50 วินาที ถ้าเกินหรือ reply ล้มเหลวจึงใช้ push
ทำเพื่ออะไร: ประหยัดโควตา และเป็นเหตุผลที่ระบบ ไม่ส่งข้อความ "ขอผมคิดก่อนครับ..." เพราะจะทำให้คำตอบจริงต้องเป็น push ทุกครั้ง

3.4 จุดเด้ง "กำลังพิมพ์" (Loading animation)

ก่อนเริ่มประมวลผลข้อความหรือการกดปุ่ม ระบบเรียก /v2/bot/chat/loading/start (60 วินาที) จุดเด้งหายเองทันทีที่คำตอบถึง

ทำเพื่ออะไร: คำถามบางข้อใช้ 5–20 วินาที ถ้าไม่มีสัญญาณอะไรผู้ใช้จะคิดว่าบอทค้าง จุดเด้ง ไม่นับโควตา และถ้าเรียกไม่สำเร็จก็ไม่ขวางการตอบ (แสดงเฉพาะแอปบนมือถือ ไม่แสดงบน LINE คอมพิวเตอร์ — ข้อจำกัดของ LINE)

3.5 ลำดับข้อความของผู้ใช้คนเดียวกัน

ข้อความของผู้ใช้คนเดียวกันถูกประมวลผลทีละข้อ (lock ต่อผู้ใช้)

ทำเพื่ออะไร: ถ้าผู้ใช้พิมพ์ 2 ข้อความติดกัน ข้อความที่สองต้องเห็นโปรไฟล์และประวัติที่ข้อความแรกบันทึกไว้แล้ว ไม่อย่างนั้นข้อมูลจะเขียนทับกัน

3.6 Rich Menu

เมนู 4 ปุ่มด้านล่างแชท: โปรไฟล์ (ส่งข้อความ "โปรไฟล์ของฉัน"), ถามบอต, ล้างข้อมูล (postback action=delete_prompt), หาคู่ (ส่ง "หาคู่ให้หน่อย") ภาพขนาด 1520×1035 ตรวจด้วย app/check_line.py

ทำเพื่ออะไร: ผู้ใช้ใหม่ไม่ต้องเดาว่าต้องพิมพ์อะไร และปุ่มลบใช้ postback ซึ่งผู้ใช้พิมพ์ปลอมเองไม่ได้

4. การลงทะเบียนครั้งแรกและความยินยอม

ลำดับ: เพิ่มเพื่อน → ข้อความต้อนรับ + ขอความยินยอมใช้ข้อมูลเพื่อจับคู่ → เพศ → เพศที่สนใจ (ชาย / หญิง / ทุกเพศ) → อายุ (18–40) → คณะ → พร้อมใช้งาน

  • ถ้า ไม่ยินยอม ยังปรึกษาเรื่องความรักได้ตามปกติ แต่จะไม่ถูกจับคู่ และไม่ถูกแนะนำให้ใครเห็น
  • ผู้ใช้แต่ละคนได้เลขผู้ใช้ L0001, L0002, … จากตัวนับใน DB ที่ ไม่นำเลขกลับมาใช้ซ้ำ
ทำเพื่ออะไร: ความยินยอมมาก่อนการเก็บข้อมูลเพื่อจับคู่ ส่วนเลขผู้ใช้ที่ไม่ใช้ซ้ำแก้บั๊กจริง: เดิมใช้ "จำนวนผู้ใช้ + 1" เมื่อมีคนลบบัญชีแล้วคนใหม่สมัคร จะได้เลขซ้ำกับคนที่ยังอยู่ (ระบบล้มด้วย IntegrityError) และอาจได้เลขของคนที่ลบไป ซึ่งยังถูกอ้างถึงในข้อมูลของผู้ใช้อื่น

5. การแยกเจตนาของข้อความ (Intent)

5.1 ปัญหาของการดักคำตายตัว

เดิมใช้รายการคำ เช่น ข้อความมีคำว่า "ลบข้อมูลของฉัน" = สั่งลบ ปัญหาจริงจาก log: ผู้ใช้พิมพ์ "ลบโปรไฟล์" หรือ "ส่งลบโปรไฟล์" ซึ่งไม่อยู่ในรายการ ระบบจึงส่งไปตอบคำปรึกษา แล้วตอบว่า "ไม่มีข้อมูลในคลัง" และหลังการ merge branch หนึ่ง ข้อความที่ไม่ใช่คำสั่ง ทั้งหมด ถูกส่งไปตอบคำปรึกษา ทำให้แชทที่เรียนรู้โปรไฟล์ไม่ทำงานเลย

5.2 วิธีใหม่ 3 ชั้น (app/intent_model.py)

  1. SBERT (bge-m3): แปลงข้อความเป็นเวกเตอร์ แล้วเทียบ cosine กับประโยคตัวอย่างของแต่ละเจตนา (8 เจตนา ราว 6–12 ประโยคต่อเจตนา) คะแนนของเจตนา = ค่าเฉลี่ยของ 2 ตัวอย่างที่ใกล้ที่สุด
  2. BM25 บน character trigram: คะแนนคำที่ใช้ร่วมกัน (ภาษาไทยไม่เว้นวรรคระหว่างคำจึงใช้ตัวอักษร 3 ตัวติดกัน) ใช้แค่เสนอตัวเลือก ไม่ใช้ตัดสิน
  3. LLM Local (qwen2.5 7B): ใช้เฉพาะเมื่อ SBERT ก้ำกึ่ง (ความคล้ายสูงสุด < 0.55 หรือห่างอันดับสองน้อยกว่า 0.04) และเลือกได้เฉพาะจากตัวเลือกอันดับต้น

เจตนาทั้งหมด: find_match, show_profile, delete_me, unmatch, recall_memory, ask_advice, followup (→ ask_advice), chat

ทำไม BM25 ห้ามตัดสิน: วัดจริงแล้ว "ลบโปรไฟล์" SBERT ให้ delete_me 0.82 vs show_profile 0.75 (ถูก) แต่ trigram "โปรไฟล์" ตรงกับตัวอย่าง "ดูโปรไฟล์" ถ้าให้คะแนนรวมตัดสินจะกลายเป็นดูโปรไฟล์ ความต่างอยู่ที่คำกริยา "ลบ" ซึ่งเป็นเรื่องความหมาย
ทำไมใช้ LLM Local: ข้อความผู้ใช้ไม่ออกนอกเครื่อง และใช้เพียงราว 1 ใน 5 ข้อความ (ข้อความที่ชัดเจนตัดสินด้วย SBERT ใน ~14 ms)

5.3 ลบข้อมูลต้องกดยืนยันเสมอ

เมื่อเจตนาเป็น delete_me บอทส่งปุ่ม "ยืนยันลบ" / "ยกเลิก" ก่อนทุกครั้ง

ทำเพื่ออะไร: การตีความความหมายอาจพลาด และการลบย้อนกลับไม่ได้ การกดยืนยันทำให้ความผิดพลาดของตัวแยกเจตนาไม่กลายเป็นความเสียหาย

7.2 การเก็บเอกสารจากเว็บ — pipelines/ingest/collect.py

ดาวน์โหลด HTML → ดึงเฉพาะเนื้อหาบทความ → ตัดส่วนท้ายที่ไม่ใช่เนื้อหา (เครดิตผู้เขียน, แท็ก, รายการอ้างอิง, ลิงก์บทความอื่น) → สร้าง PDF ที่มีหัวอ้างอิง (ชื่อ / หน่วยงาน / URL / วันที่เข้าถึง) → ตรวจว่าอ่านกลับได้ตรงต้นฉบับ

ปัญหาที่เจอและแก้: การสร้าง PDF ด้วยการจัดรูปอักษร (glyph shaping) ทำให้ไม้เอก ไม้โท ทัณฑฆาต หายจาก text layer ราว 7% ในทุกฟอนต์ไทยของเครื่อง จึงเปลี่ยนเป็นการวางตัวอักษรทีละตัว ผล: อ่านกลับได้ตรงต้นฉบับ 99.7–100% (หายเฉพาะอีโมจิ)

7.3 OCR สำหรับเอกสารสแกน

  • ใช้ VLM (qwen2.5vl) อ่านภาพหน้าเอกสาร
  • ตัดขอบล่าง 6% ก่อนอ่าน เพราะคลังวิทยานิพนธ์ประทับตรา "ดาวน์โหลดเมื่อ…" ทุกหน้า
  • อ่าน 2 รอบ แล้วให้ WangchanBERTa (masked LM ภาษาไทย) เลือกคำที่เป็นไปได้กว่าในจุดที่ 2 รอบไม่ตรงกัน เลือกเฉพาะเมื่อมั่นใจ ที่เหลือเก็บไว้ให้คนตรวจ
  • หน้าที่คนตรวจจากภาพแล้ว (101 หน้า) ใช้แทนผล OCR

ผล: CER 8.0% → 4.3%, WER 14.6% → 11.2% (วัดกับหน้าที่ถอดด้วยมือ ocr_eval.py)

ทำเพื่ออะไร: ตัวอักษรที่ OCR ผิดทำให้ค้นไม่เจอและทำให้คำตอบอ้างข้อความผิด หน้าผลการวิจัย (บท 4–5) ซึ่งตอบคำถามเรื่องการเริ่มจีบโดยตรงจึงถูกตรวจด้วยคนทุกหน้า

7.6 Metadata และ Concept

แต่ละ chunk มี: chunk_id คงที่, ที่มา (source / ชื่อ / ปี), ชนิดเอกสาร, ระดับความน่าเชื่อถือ, บท / หน้า, หมวด (ใช้ใน router), concept (taxonomy id ชุดเดียวกับโปรไฟล์ผู้ใช้), หัวข้อย่อย

ติด concept ด้วย lexicon + กฎบริบท:

  • คำกำกวมต้องมีคำบริบทใกล้ๆ ภายใน ±60 ตัวอักษร (เช่น "มั่นคง" ต้องอยู่ใกล้ "ผูกพัน / secure")
  • not_after: ไม่นับถ้าตามหลังคำปฏิเสธ ("ไม่มั่นคง" ไม่ใช่ secure)
  • not_before: ไม่นับถ้าคำต่อท้ายทำให้เป็นคำอื่น ("ความมั่นคงปลอดภัยไซเบอร์", "รู้สึกผิดหวัง")
  • ข้ามคำที่ถูกปฏิเสธ เช่น "ไม่รับผิดชอบ", "การไม่นอกใจ", "ไม่พูดหลอกลวง"
  • เอกสารการแพทย์และงานวิจัยภาษาศาสตร์ไม่ติด concept (คำว่า "สนิท" ในงานภาษาศาสตร์ = ความคุ้นเคย ไม่ใช่ความใกล้ชิดแบบคู่รัก)

สุ่มตรวจ 50 คู่ (chunk, concept): ถูก 76% → แก้คำปฏิเสธแล้ว 80.9% ในชุดเดิม (ผู้ตรวจ: Claude — ควรให้คนตรวจยืนยันและสุ่มชุดใหม่) · ทดลองบังคับให้คำตรงรอยตัดคำแล้ว ไม่ใช้ เพราะแก้ได้ 1 ข้อแต่ทำ tag ที่ถูกหายไป 6 ข้อ

ทำเพื่ออะไร: concept คือสะพานระหว่างคลังความรู้กับกราฟและโปรไฟล์ผู้ใช้ ถ้า tag ผิด กราฟจะดึงความรู้ที่ไม่เกี่ยวมาตอบ รายละเอียดทั้งหมดอยู่ใน docs/data_card.md

8. Dense RAG

8.1 ฝั่งตอบเอกสาร

  • ทุก chunk แปลงเป็นเวกเตอร์ด้วย BAAI/bge-m3 (โมเดลหลายภาษาที่รองรับไทย) เก็บใน ChromaDB (cosine)
  • ค้นด้วยทุกแบบของคำถาม (คำถามเดิม + คำพ้อง) แล้วรวมผล
  • จำกัด 3 chunk ต่อแหล่ง — วิทยานิพนธ์เล่มใหญ่ (200+ chunk) เคยยึดผลค้นทั้งหมดจนแหล่งอื่นที่ตอบตรงหลุด

8.2 ฝั่งหาคู่

  • แต่ละคนมีเวกเตอร์ "ตัวตน" (persona) และ "สเปคที่อยากได้" (preference)
  • คะแนน = ค่าเฉลี่ยฮาร์มอนิกสองทาง: A อยากได้แบบ B และ B อยากได้แบบ A (ฮาร์มอนิกลงโทษคู่ที่ชอบอยู่ฝ่ายเดียว)
  • หักคะแนนถ้าผู้สมัครคล้ายคนที่ผู้ใช้เคยปัดทิ้ง (λ = 0.15)
จุดอ่อนที่รู้: embedding แยกความหมายตรงข้ามได้แย่ เช่น "อยากมีลูก" กับ "ไม่อยากมีลูก" (cosine 0.70 vs 0.63) จึงต้องให้ LLM อ่านค่านิยมเป็นโครงสร้างแยก (ข้อ 12.3)

10. การค้นความรู้แบบ Hybrid สำหรับตอบคำปรึกษา

10.1 ขยายคำ — pipelines/hybrid/query_expand.py

  • คำเรียกอีกฝ่าย: ผู้ใช้พูด "คนคุย / เค้า / คนที่ชอบ" เอกสารเขียน "แฟน / คู่รัก / อีกฝ่าย" → ค้นทั้งแบบเดิมและแบบแทนเป็นคำกลาง ("เพื่อน" แทนเมื่อไม่มีคำอื่น เพราะ "นัดเพื่อนกับแฟน" ต้องไม่กลายเป็นแฟนกับแฟน)

  • อื่นๆ → hybrid
  • chunk หมวดสุขภาพทางเพศใช้ได้ เฉพาะเมื่อคำถามเกี่ยวกับสุขภาพ

10.3 ด่านความเกี่ยวข้อง — pipelines/hybrid/gate.py

ให้ cross-encoder bge-reranker-v2-m3 อ่านคำถามคู่กับเอกสารทีละคู่ (อ่านจริงทั้งสองฝั่ง ต่างจาก SBERT ที่เทียบเวกเตอร์) แล้วเก็บเฉพาะเอกสารที่:

  • ได้คะแนน ≥ 0.1 และ
  • ได้คะแนน ≥ 30% ของอันดับ 1 (ตัดชิ้นที่ห่างจากชิ้นที่ตรงที่สุดมาก)

ใช้คะแนนสูงสุดของทุกแบบคำถาม · เอกสารยาวอ่านเป็นช่วงละ 600 ตัวอักษรซ้อน 150 · กฎจากกราฟ ถูกแปลงเป็นประโยคธรรมดาก่อนให้คะแนน (ข้อความที่ส่งให้ LLM ไม่เปลี่ยน) · เรียงลำดับสุดท้ายตามคะแนนความเกี่ยวข้อง

ทำไมต้องมีด่านนี้: การค้นเวกเตอร์ "เจอเสมอ" แม้คำถามจะอยู่นอกคลัง (ค้นอย่างเดียว empty_on_unanswerable = 0/11) ด่านนี้คือชั้นแรกที่ทำให้บอทตอบว่า "ไม่มีข้อมูล" ได้ · ทำไมแปลงกฎเป็นประโยค: reranker ไม่เข้าใจรูปแบบลูกศร "(A) -[CONFLICTS_WITH]-> (B)" วัดจริง "anxious กับ avoidant เข้ากันไหม" 0.00 → 0.96 · ทำไมเรียงตามความเกี่ยวข้อง: "ควรเริ่มทักยังไงดี" เคยได้ chunk ที่ตอบตรง (0.884) คู่กับบทความคนขี้อาย (0.107) เพราะเรียงตามคะแนนค้นเดิม

10.4 รอบแปลงคำถาม (เมื่อรอบแรกไม่เจอ) — pipelines/hybrid/search.py

ถ้ารอบแรกได้เอกสารที่เกี่ยวข้องสูงสุด < 0.3 ให้ LLM เขียนคำถามใหม่ 3 บรรทัด:

  1. คำถามเดิมที่ตัดรายละเอียดเฉพาะตัว (ชื่อ สถานที่ ตัวเลข จำนวนเงิน เหตุผลที่อีกฝ่ายอ้าง)
  2. พฤติกรรมหลักของอีกฝ่าย + ถามว่าเป็นสัญญาณหรือความเสี่ยงอะไร
  3. คำถามที่กว้างที่สุดของหัวข้อนั้น

LLM ได้รับ รายชื่อหัวข้อในคลัง 36 หัวข้อ ด้วย เพื่อเขียนด้วยคำแบบเอกสาร จากนั้นค้นใหม่ + ดึง chunk ก่อน/หลังของชิ้นที่ผ่านด่านมาให้คะแนนด้วย ใช้ผลรอบ 2 เฉพาะเมื่อดีกว่ารอบแรก และ ไม่ให้คะแนนคู่ที่รอบแรกให้ไปแล้วซ้ำ (ผลเท่าเดิมทุกตัว เร็วขึ้นราว 25%)

ทำเพื่ออะไร: ผู้ใช้เล่าสถานการณ์เฉพาะตัว แต่เอกสารเขียนเป็นหลักการทั่วไป · วัดจริง: "คนคุยขอเงินไปจ่ายค่าเทอม ควรให้ไหม" รอบแรก 0.00 → แปลงเป็น "การที่คนคุยขอเงินเป็นสัญญาณของ Romance Scam หรือไม่" ได้บทความตำรวจ 0.85 · "เค้าถามเรื่องส่วนตัว เปลี่ยนเรื่องยังไงดี" เจอบทความ Healthy Boundary c04 (0.61) ที่เคยหลุดเพราะจำกัด 3 chunk ต่อแหล่ง จึงต้องดึง chunk ข้างเคียง · หัวข้อจาก LLM ใช้ค้นเท่านั้น คำตอบยังต้องผ่านด่านเดิมทุกด่าน

11. การสร้างคำตอบด้วย LLM และการกันตอบเกินคลังความรู้

11.1 กฎใน prompt (7 ข้อ)

  1. ใช้ข้อมูลใน CONTEXT เท่านั้น ห้ามใช้ความรู้ของตัวเอง ห้ามแต่งเพิ่ม
  2. ทุกประโยคที่ใช้ข้อมูลต้องลงท้ายด้วยเลขอ้างอิง [n]
  3. ถ้าไม่มีข้อมูลที่ตอบได้ ให้ตอบ "ไม่มีข้อมูลเพียงพอ" เท่านั้น
  4. ถ้า CONTEXT แค่ใกล้เคียงแต่ไม่ได้ตอบตรง ให้ตอบว่าไม่มีข้อมูล ห้ามหยิบเรื่องอื่นมาตอบแทน
  5. สรุปด้วยคำพูดของตัวเองให้ตรงคำถาม ไม่คัดลอกข้อความยาว
  6. คำเรียกอีกฝ่าย (คนคุย / เค้า) = แฟน / คู่รัก / อีกฝ่าย ในเอกสาร
  7. ห้ามเปลี่ยน "ตัวอย่าง" หรือเรื่องเล่าของคนอื่นเป็นคำแนะนำว่า "ควร…"

คำถามที่ส่งให้ LLM แนบคำพ้องและหัวข้อที่เอกสารใช้ด้วย ("คำในเอกสารอาจใช้คำอื่นที่หมายถึงเรื่องเดียวกัน เช่น: …") ส่วนประวัติแชทถูกส่งไปพร้อมกฎว่า "ใช้เพื่อเข้าใจสถานการณ์เท่านั้น ไม่ใช่หลักฐาน ใช้เลขอ้างอิงจาก CONTEXT รอบนี้เท่านั้น"

ทำไมต้องแนบคำพ้อง: วัดจริง: แม้ context จะมีคำตอบ LLM ก็ตอบ "ไม่มีข้อมูล" สำหรับ "ควรเริ่มทักยังไงดี" เพราะไม่รู้ว่า "ทัก" คือ "เริ่มต้นความสัมพันธ์" แนบแล้วตอบได้และผ่านการตรวจหลักฐาน

11.2 ตรวจหลักฐานหลังตอบ — verify_answer

ตัดคำตอบเป็นท่อน (≥ 40 ตัวอักษร) แล้วให้ cross-encoder เทียบแต่ละท่อนกับเอกสารที่ถูกอ้าง ท่อนที่ได้ < 0.1 หรือแค่ทวนคำถามถูกตัดทิ้ง ถ้าไม่เหลืออะไร → ตอบว่าไม่มีข้อมูล

ทำไมตรวจทีละท่อน ไม่ใช่ทีละย่อหน้า: LLM มักใส่อ้างอิงครั้งเดียวท้ายย่อหน้า ถ้าให้คะแนนทั้งย่อหน้า ท่อนที่แต่งเพิ่มจะได้คะแนนของท่อนจริงไปด้วย · วัดจริง: ประโยคแต่งเกิน "คุยแชทบ่อยๆ เพื่อให้ความสัมพันธ์ดีขึ้น" ได้ 0.008 ส่วนประโยคที่มีหลักฐานจริงต่ำสุด 0.568 เกณฑ์ 0.1 จึงแยกได้ชัด · ทำไมตรวจคำทวนคำถาม: LLM เคยตอบแค่ "จีบรุ่นพี่ในคณะดีไหม [10]"

11.3 ทำความสะอาดก่อนส่ง

  • ตัด markdown (**, #, `) เพราะ LINE ไม่แสดงผล
  • ชื่อแหล่งที่ดูเหมือนโดเมนถูกทำให้ไม่เป็นลิงก์ (LINE แปลง "xxx.co" เป็นลิงก์อัตโนมัติ)
  • บรรทัดท้าย "📚 อ้างอิง:" แสดงชื่อเอกสารที่ถูกอ้างจริง ไม่เกิน 3 แหล่ง

12. การเรียนรู้โปรไฟล์ผู้ใช้จากแชท

12.1 สกัดโปรไฟล์ — app/flows/chat.py

ทุกข้อความแชท LLM Local (qwen2.5 7B, ผลลัพธ์ตาม JSON schema) สกัดงานอดิเรก นิสัย สไตล์การสื่อสาร สิ่งที่อยากได้ สิ่งที่ไม่เอา เป็น taxonomy id แล้วรวมเข้าโปรไฟล์ ข้อความเรื่องคณะหรือค่านิยมจะไม่ถูกใช้เดานิสัย (เช่น "วิศวะ" ไม่ได้แปลว่า "มีเหตุผล")

  • ของเดิมเพิ่ม confidence และจำนวนหลักฐาน ข้อมูลไม่โตตามจำนวนแชท (งานอดิเรกไม่เกิน 8, นิสัยไม่เกิน 6)

12.2 เปลี่ยนใจ

  • คำว่า "เปลี่ยนใจ / เปลี่ยนเป็น / แก้เป็น / ไม่เอาแล้ว / ตอนนี้ชอบ / …แทน" → กลุ่มที่เลือกได้ค่าเดียว (สีผิว, รูปร่าง) ใช้ค่าใหม่แทนค่าเดิม ส่วนนิสัยและงานอดิเรกไม่ลบของเดิม
  • สิ่งที่เปลี่ยนเป็น "ไม่ชอบ" ถูกเอาออกจาก "อยากได้" และกลับกัน
  • คณะ: เปลี่ยนใจ = แทนของเดิม, "ไม่จำกัดคณะ" = ล้างรายการ
ปัญหาจริง: "ผิวขาว" แล้ว "เปลี่ยนใจชอบผิวดำ" เคยได้โปรไฟล์ "ผิวขาว, ผิวเข้ม" ที่ขัดกันเอง · บั๊กที่เทสต์เจอระหว่างแก้: "ผิวแทน" มีคำว่า "แทน" จึงไม่นับ "แทน" ที่อยู่หลัง "ผิว / สี" · ข้อจำกัด: คำว่าเปลี่ยนใจยังเป็นรายการคำ

14. หลังแนะนำคู่

14.1 ทำความรู้จัก (mutual consent) — app/flows/intro.py

  1. A กด "สนใจทำความรู้จัก" บนการ์ดของ B
  2. ระบบส่งการ์ดของ A ให้ B ประเมิน ยังไม่มีช่องทางติดต่อของใคร
  3. B ยินยอม → ทั้งคู่ได้ LINE ID ของกันและกัน / B ไม่สะดวก → A ได้ข้อความสุภาพ ไม่ได้ข้อมูลของ B และระบบไม่แนะนำคู่นี้อีก
ทำเพื่ออะไร: ความปลอดภัยของทั้งสองฝ่าย ไม่มีใครได้ช่องทางติดต่อของคนที่ไม่ยินยอม · LINE API ไม่เปิดให้บอทเห็น LINE ID ของผู้ใช้ จึงให้ผู้ใช้ส่ง ID เอง เก็บแยก และส่งต่อเฉพาะเมื่อยินยอมทั้งคู่

14.2 ขอผ่าน

บันทึก event "pass" → ไม่แนะนำคนนี้อีก และคนที่คล้ายคนนี้จะถูกหักคะแนน Dense เล็กน้อย

14.3 เลิกคุย — app/flows/unmatch.py

  1. ถามเหตุผลสั้นๆ
  2. LLM แยกเหตุผลเป็น: พฤติกรรมของอีกฝ่าย / สเปคของผู้พูด (อยากได้-ไม่เอา) / รูปลักษณ์
  3. นโยบาย: เฉพาะพฤติกรรม (red flag) เท่านั้นที่นับเป็นการรายงานอีกฝ่าย และมีผลเมื่อรายงาน ≥ 3 คน ส่วนเรื่องรูปลักษณ์ / สเปคใช้ปรับสเปคของผู้พูดเท่านั้น ไม่ลงโทษอีกฝ่าย
  4. ครั้งต่อไปลดน้ำหนักและคัดกรองคนที่มีพฤติกรรมแบบนั้น
ทำไมต้อง ≥ 3 คนและไม่นับรูปลักษณ์: กันการกลั่นแกล้งด้วยการรายงานคนเดียว และไม่ลงโทษใครเพราะหน้าตาหรือสีผิว ซึ่งเป็นความชอบส่วนตัวของผู้พูด ไม่ใช่ข้อบกพร่องของอีกฝ่าย

17. ความเป็นส่วนตัวและความปลอดภัย

  • ความยินยอม: ก่อนจับคู่ และแยกอีกครั้งสำหรับศาสนา / อาหาร / สีผิว
  • ไม่ส่งข้อมูลอ่อนไหวให้ API: ศาสนา อาหาร แชทดิบ LINE ID เบอร์ อีเมล · ความจำสรุปด้วย LLM Local
  • สิทธิ์ลบข้อมูล: ลบโปรไฟล์ ความจำ ประวัติแชท event คำแนะนำ ช่องทางติดต่อ และโหนดใน Neo4j ต้องกดยืนยันก่อน
  • ความโปร่งใส: ผู้ใช้ดูได้ว่าระบบจำอะไร อีกฝ่ายไม่เห็นสิ่งที่ผู้ใช้คุยกับบอท
  • ช่องทางติดต่อ: ส่งต่อเฉพาะเมื่อยินยอมทั้งสองฝ่าย
  • ความลับของระบบ: .env (API key, LINE token), graph/.env และฐานข้อมูลแชทจริง (*.db) อยู่ใน .gitignore
  • ลิขสิทธิ์: เอกสารส่วนใหญ่มีลิขสิทธิ์ ใช้เพื่อการศึกษา repo ต้องเป็น private และคำตอบอ้างอิงแหล่งทุกครั้ง
  • คำตอบเรื่องสุขภาพ: ตอบจากเอกสารการแพทย์เท่านั้น และไม่ถูกดึงไปตอบคำถามเรื่องความสัมพันธ์ทั่วไป

18. ข้อจำกัดที่รู้อยู่และงานที่ควรทำต่อ

  1. คำถามที่ต้องอนุมาน ตอบว่าไม่มีข้อมูล (กฎข้อ 4 แบบเข้ม) — ทางแก้: เพิ่มเอกสาร หรือผ่อนกฎโดยต้องบอกว่า "เอกสารไม่ได้พูดตรงๆ"
  2. API ไม่ deterministic ผลต่อข้อสลับได้ระหว่างรอบ — ทางแก้: จำคำที่แปลงแล้วของคำถามเดิม และรายงานผลเฉลี่ยหลายรอบ
  3. ยังใช้กฎคำ: คำถามต่อเนื่อง, การเปลี่ยนเรื่อง, การเปลี่ยนใจ, คำสัญญาณสุขภาพใน router
  4. กฎความเข้ากัน 14 กฎ ยังไม่ผูกกับหลักฐานงานวิจัย
  5. concept tag ยังผิดความหมายบางกรณี และ tag จากบรรณานุกรม — ต้องให้คนตรวจ
  6. คำตอบเรื่องสุขภาพเร่งด่วน (เช่น ถุงยางแตก) ควรมีกฎให้แนะนำพบแพทย์ โดยอ้างจากเอกสาร
  7. ยังไม่มี gold set ที่คนตรวจ, ชุด red-team (prompt injection / ขอข้อมูลผู้ใช้อื่น), ผลเปรียบเทียบโมเดล 4 กลุ่ม, latency p50/p95 ระดับระบบ
  8. ข้อมูลผู้ใช้เป็นข้อมูลสังเคราะห์ ผลจับคู่วัดกลไก ไม่ใช่ความพึงพอใจของผู้ใช้จริง
